# 需求驱动的 Skill 创建

帮助用户从实际问题出发，判断要解决的需求，再设计、创建并验证相应的 Skill。不要把用户最初提出的功能或方案直接当成根本需求。

## 需求访谈

先了解具体经历，再讨论抽象方案。根据用户已经提供的信息继续，不重复提问；把彼此依赖的问题分轮提出，并在每个问题下给出清楚的推荐选项和理由。

围绕会改变 Skill 设计的要点了解情况：

- 最近发生的具体场景、涉及的人和当时的目标
- 用户观察到的问题、造成的影响和目前的应对方式
- 用户期待的结果，以及如何判断结果有改善
- 使用环境、约束和失败代价

把观察到的症状、用户对原因的解释、其他可能原因和已确认的需求分开。必要时提出多个合理解释，并用具体经历核对，不用连续追问“为什么”代替分析。需要事实时先查可用的文件、工具或环境；不要让用户提供本来可以自行查到的信息。无法核实的内容要标为未知或假设。

当具体场景、期望结果、足以影响设计的原因、关键约束和成功判断都已清楚，且没有悬而未决的重要问题时，向用户简要复述你的理解，并请用户确认。不要声称找到了唯一或绝对的根因；目标是找到足以指导方案、且经用户认可的需求层次。用户确认前不进入 Skill 设计和文件创建。

## 判断方案

确认需求后，判断 Skill 是否适合解决它。如果脚本、配置、流程调整或其他方案可能更合适，说明原因和主要取舍，给出建议并让用户选择；不要擅自改变用户要创建 Skill 的目标。

把用户的 Workflow / 方法论区分作为默认分析框架，而不是不可更改的定律：

- Workflow 组织步骤、顺序和交接。
- 方法论提供判断原则、推理方式或操作指导。
- 一个 Skill 可以偏向其中一种，也可以结合两者。
- 渐进式披露是组织 Skill 内容的方式；参考资料、脚本和素材是可选支持材料，不必当作新的底层类型。

根据需求确定 Skill 的适用场景、触发描述、输入输出、必要流程与指导、边界，以及是否确实需要参考文件或脚本。不要为了完整而添加无用的目录、规则或资源。

## 创建与验证

把设计方案和关键取舍简要交给用户确认后再创建或大幅修改文件。尊重用户指定的名称、位置和格式；未指定时，根据目标平台和使用场景选择合适的默认位置，不确定且会造成不同结果时先询问。

按目标平台的 Skill 规范创建最小可用结构，确保描述能准确说明用途和适用时机。新建或实质性重构后：

1. 使用该平台提供的结构验证工具检查 frontmatter、命名和文件结构。
2. 检查指令是否落实了已确认的需求、用户边界和触发范围。
3. 用至少一个贴近真实场景的请求走查访谈、需求确认、方案判断和交付流程；按实际发现的问题修正。

验证工具无法运行时，说明缺少的依赖或原因，不要宣称验证通过。完成后总结需求结论、方案类型、文件位置和验证结果，并明确仍未验证的部分。
